# 跑接口用例并汇报

用 MCP 工具 `apitest` 完成。**只用工具拿事实，不要凭印象编造结果。**

## 步骤

1. **确定范围**
   - 用户说了项目/模块就直接用。
   - 没说就先 `list_modules` 列出模块，挑一个最相关的，**说明为什么选它**。
   - 用户只说了"跑一下"没给范围 —— 先问清楚，不要跑全量。

2. **执行**
   `run_cases(project=..., module=...)`
   - 范围大时先加 `mark`（用 `list_marks` 查有哪些标签）
   - **只给 `project` 会被工具拒绝** —— 那等于跑整个项目。至少要带
     `module` / `mark` / `case_file` / `case_id` 之一
   - 超时了就把范围缩小，不要盲目调大 timeout

3. **归因**
   有失败就调 `diagnose_failures()`。默认只用规则（免费、秒出）；
   用户明确要求深挖时才传 `use_ai: true`。

4. **汇报**，固定这个结构：

   ```
   ## 执行结果
   总数 / 通过 / 失败 / 跳过，耗时

   ## 失败清单
   用例名 | 归因 | 一句话原因 | 下一步

   ## 结论
   环境问题 N 条 → 建议重跑
   服务问题 N 条 → 需要提缺陷
   用例数据问题 N 条 → 可走自愈流程
   ```

## 硬性要求

- **归因为「服务问题」的用例，绝不建议改断言让它变绿。** 这是底线，
  用改断言掩盖真实缺陷比不修更糟。
- 失败原因必须引用 `diagnose_failures` 的输出，不要自己推测。
- 不要把终端输出整段贴给用户，只给结论和关键证据。
- 没跑起来（`ok: false`）就如实说没跑起来，不要报一个假的"全部通过"。

## 常见情况

| 现象 | 怎么办 |
|---|---|
| `run_cases` 报"必须指定筛选条件" | 这是设计如此，先 `list_modules` 挑范围 |
| `run_cases` 报"只给 project 会跑掉全部用例" | 补一个 `module` 或 `mark`；真要跑整项目请用户确认后用命令行跑 |
| 全部失败且都是连接错误 | 大概率环境不通，`diagnose_failures` 会归到环境问题；先确认被测服务活着 |
| 失败集中在登录相关用例 | 先单独跑 auth 模块，登录通了再跑别的 |
| 同一批用例上次通过这次全挂 | 优先怀疑环境（token 过期、服务重启），而不是用例坏了 |
