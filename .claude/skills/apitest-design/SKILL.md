# 接口测试设计（维度矩阵）

**核心原则：先设计测点，再生成用例。模型只负责把测点填成具体请求和断言，不负责决定"测什么"。**

只生成正例的用例集，通过率再高也没有信息量。判断一套用例好不好，看**维度覆盖**，
不看通过率。

## 一、维度矩阵

每个测点都必须能回答三个问题：**为什么测（依据）、期望什么、测不到算什么**。

### A. 参数契约（依据：接口元数据）

| ID | 维度 | 触发条件 | 期望 | 优先级 |
|---|---|---|---|---|
| A1 | 必填缺失 | `required=true` 的字段 | 被拒绝 | P1 |
| A2 | 类型错误 | 字段类型已知（string/int/bool/array） | 被拒绝 | P1 |
| A3 | 枚举非法 | `enum` 已定义 | 被拒绝 | P1 |
| A4 | 长度边界 | `minLength` / `maxLength` 已知 | 下界-1、下界、上界、上界+1 | P2 |
| A5 | 格式非法 | `format=email/phone/date/url` | 被拒绝 | P2 |
| A6 | 空值 / null | 必填的 string/array | 被拒绝 | P2 |
| A7 | 多余字段 | 请求体 | 按项目契约：忽略或拒绝 | P3 |

### B. 业务语义（依据：参数含义 + 现役用例）

| ID | 维度 | 触发条件 | 期望 | 优先级 |
|---|---|---|---|---|
| B1 | 分页边界 | 有 `page/current/size/limit` | page=0、size=0、size 超上限 | P1 |
| B2 | 排序 / 过滤 | 有 `sort/order/status/type` 等 | 排序生效、过滤结果是子集 | P2 |
| B3 | 幂等 / 重复提交 | 写接口有唯一键 | 第二次结果一致或明确冲突 | P2 |
| B4 | 状态迁移 | 有 `status/enabled/audit` 等状态字段 | 合法迁移成功、非法迁移被拒 | P2 |

### C. 权限（依据：项目登录配置 + 角色体系）

| ID | 维度 | 触发条件 | 期望 | 优先级 |
|---|---|---|---|---|
| C1 | 未登录 | 接口需要登录 | 401 / 业务未授权码 | P0 |
| C2 | 无权限角色 | 系统有角色/权限模型 | 403 / 业务无权限码 | P1 |
| C3 | token 失效 / 伪造 | 接口需要登录 | 未授权 | P2 |

### D. 数据一致性（依据：知识图谱映射，置信度 ≥ 0.9）

| ID | 维度 | 触发条件 | 期望 | 优先级 |
|---|---|---|---|---|
| D1 | 响应字段 vs 库 | 图谱有 `字段→表.列` 且 confidence ≥ 0.9 | 响应值与库值一致 | P1 |
| D2 | 写后能查到 | 写接口 | 造数后 `db_query_exists` | P1 |
| D3 | 删后查不到 | 删接口 | 清理后 `db_query_not_exists` | P1 |
| D4 | 跨表一致 | 主表 + 关联表已知 | 主表/关联表同时正确 | P2 |

> confidence < 0.9 的映射**不许自动写落库断言**——猜错的断言比没有断言更糟。

### E. 接口关联（依据：图谱的 producer→consumer 依赖）

| ID | 维度 | 触发条件 | 期望 | 优先级 |
|---|---|---|---|---|
| E1 | 创建→查询→修改→删除 | 同一资源有完整 CRUD | 全链路一致 | P1 |
| E2 | FK 依赖 | 子资源需要父资源 id | 先造父资源，再调子接口 | P1 |
| E3 | 清理隔离 | 所有写操作 | 只删本用例造的数据 | P0 |

### F. 异常与健壮性（依据：参数类型 + 资源语义）

| ID | 维度 | 触发条件 | 期望 | 优先级 |
|---|---|---|---|---|
| F1 | 不存在的 id | 路径/参数是 id | 业务失败 / 空数据 | P2 |
| F2 | 已删除的 id | 资源支持删除 | 业务失败 / 空数据 | P3 |
| F3 | 非法 path 参数 | 路径参数有类型约束 | 被拒绝，不 500 | P2 |
| F4 | 超大 body / 特殊字符 | 文本字段 | 被拒绝或安全处理，不 500 | P3 |

## 二、证据分级

每个测点必须标依据来源，**没有依据的测点不许当成已验证用例**：

1. **E1 接口元数据**：required / type / enum / bounds / format
2. **E2 知识图谱**：字段→表列，confidence ≥ 0.9
3. **E3 现役已通过用例**：项目契约、真实数据
4. **E4 项目配置**：登录方式、成功码、失败语义
5. **A 假设**：以上都没有 → 标 `needs_manual_setup`，`draft`，不进 CI

## 三、最小交付标准

按接口类型算"应测维度"，达不到就不算覆盖完：

| 接口类型 | 必须覆盖 |
|---|---|
| 只读查询 | 正例 + A 类（有元数据时至少 2 个） + D1（有映射时） |
| 分页查询 | 上述 + B1 |
| 写操作（POST/PUT/PATCH） | 正例 + A 类 + D2 + E2/E3 |
| 删除操作 | 正例 + D3 + F1 + E3 |
| 需要登录的接口 | + C1 |
| 有角色模型的系统 | + C2 |
| 有完整 CRUD 的资源 | + E1 |

**多步场景链**：一条链写在一行里（Excel「步骤」列，JSON 数组；`create_case(steps=[...])`），
不要拆成几条互不相干的用例。闸门按整条链判：

- 断言跨步骤汇总，但**验证步**（最后一个读步骤）必须至少有 1 个业务断言 ——
  只验写接口的回执证明不了数据真的可查
- **每个**写步骤都要有去处：挂 teardowns，或它本身是引用 setup 输出的 DELETE
- 步骤之间用 `{{步骤id.字段}}` 引用上一步的输出，不要写死 id

## 四、反模式（出现即打回）

- 只生成正例，或负例全是"必填缺失"一种
- 没有依据的反例（服务端根本没校验，断言 `not_equal code` 必然误报）
- 只断言 `status_code` / `success`，没有业务字段
- 用通过率冒充覆盖率
- 单步用例冒充场景链
- 正例写操作没有 setups/teardowns（反例的请求本就被拒绝，不要求清理）
- 落库断言用了 confidence < 0.9 的映射
- 路径参数留着 `{id}` 就发请求
- 转 debugged 时全是没有 `expected` 的结构断言（`exists` / `is_not_none` 只证明字段存在；
  转正要求 ≥ 1 条值断言，用 `get_last_result` 取真实响应补）

## 五、和生成器的关系

| 规范 | 落地位置 |
|---|---|
| 本文的机器可读版 | `ai/rules/case_rules.yaml` |
| 测点枚举 | `ai/pipeline/intents.py`（按矩阵生成 TestIntent） |
| 模型填数 | `ai/capabilities/case_gen.py`（按 intent 生成，不自由发挥） |
| 维度闸门 | `ai/pipeline/dimension_coverage.py` |
| 质量闸门（可执行） | `ai/rules/validator.py`（`create_case` / `apply_case_change` / `set_case_status` 共用） |
| 存量盘点 | `tools/maint/audit_quality.py`（只读，`--json` / `--fail` 给 CI） |
| 落盘 | `create_case`（Excel，默认 `draft`；多步链走「步骤」列） |

**改规则时先改本文，再改 `case_rules.yaml`，最后改代码。三处不一致视为 bug。**
